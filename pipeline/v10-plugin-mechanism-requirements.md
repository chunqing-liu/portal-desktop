# 星图社区插件化 + 围炉共享机制（2026-09-24 11:38 醇青需求）

> 任务类型：机制设计（doc-only）。产出设计文档 `pipeline/v10-community-plugin-design.md`，不改任何代码，不跑 git，不碰运行中进程。

## 用户原话

「并且关于大家使用的需求
这玩意应该是作为社区插件，大家下载安装使用才会有星图这个功能，然后同一个围炉里的人才能看到同一个项目任务，你看看这些机制怎么实现」

拆成两个机制问题：
1. **插件化分发**：星图不是客户端内置，而是社区插件——用户下载安装后才获得星图功能。
2. **围炉共享数据**：同一个围炉的成员看到同一个项目任务（同一份星图数据），跨成员实时/准实时同步。

## 已核实的事实（设计必须以此为边界，不要凭空假设）

### 星图现状
- 星图代码硬编码在客户端内：`desktop/renderer/pipeline/`（page.tsx、v4.css、models/templates.ts、models/bug-fix.ts），是 fork（d5z/portal-desktop 的 feature/pipeline 分支）的一部分，不是插件。
- 当前无任何插件运行时加载它——它随客户端构建发布。

### 插件系统现状（desktop/EXTENSIONS.md，2026-09-11 设计提案，未实现）
- 客户端**尚未实现**插件 SDK、界面扩展加载器或统一插件管理页。当前可用：本地 Portal Kit 导入 + Grove Kit 安装（工具类，MCP stdio）。
- 设计稿的界面插件模型 = **声明式组件**：列表、详情卡片、筛选项、设置表单、导航入口——宿主统一渲染，插件不接触 DOM/CSS/Electron IPC。
- 设计稿预留的逃生门 = **隔离网页面板**（独立来源、受限消息通道、大小/频率限制、生命周期撤销、渲染器隔离验证），条件苛刻，未实现。
- **关键张力：星图是全交互画布**（xyflow、节点拖拽、连线、滚轮缩放、站容器、专注模式、右键菜单），远超声明式组件模型的表达力。设计必须直面这个矛盾：要么走隔离网页面板路线，要么扩展插件组件模型新增 canvas 类组件，要么给出第三条路。不能假装声明式面板装得下星图。
- 插件清单拟议格式 `desktop.plugin.json`（schemaVersion/id/version/requires/capabilities/contributes.panels），能力声明必须是宿主已实现枚举。
- 实施顺序（设计稿）：①完善原生 Kit 管理 → ②最小社区界面扩展（manifest+Registry+只读 Host API+一个公开卷轴示例）→ ③分发与兼容工具 → ④按需扩展（隔离网页组件、CLI 执行适配器）。

### 围炉 API 现状（2026-09-24 从 /api/fireside/help 实测，这是全部能力面）
- 纯消息系统：create（开炉，owner 自动加入，返回 64 位 hex key）/ join（凭 key，幂等）/ leave / delete / rename / hear（since 增量读，limit ≤200）/ speak（单条 ≤32000 字符，支持 reply_to）/ revise（编辑自己发的消息，32000 上限）/ unsay（撤回）/ members（成员 town_id+显示名+加入时间）/ mentions。
- **没有** KV 存储、没有共享状态端点、没有文档/JSON 数据接口。围炉数据 = 消息流。
- 成员身份 = town_id。beings 和人类（借 client 发言，via 字段区分）都在同一消息流里。
- 客户端 Town SDK 已具备：围炉消息 UI、成员名单、SSE 增量流、Bearer/查询参数鉴权（见 desktop/TOWN-SDK.md）。星图做围炉同步时可直接复用客户端已有的 Town 连接，不需要插件自带鉴权。

### 用户生态
- 「大家」= 各自机器上跑 beings 客户端的人类 + beings。星图数据要在这些人之间共享，共享域 = 围炉（私密小圈子，key 邀请制）。
- 注意：围炉成员的客户端可能装了星图插件，也可能没装。没装的人看不到星图内容（消息里若混入星图数据，没插件的人会看到原始消息——设计要考虑这一点）。

## 要设计的问题（每个都给方案对比 + 推荐 + 风险）

### A. 星图如何打包为社区插件
- 对照 EXTENSIONS.md 的三条路（声明式面板 / 隔离网页面板 / 扩展组件模型）评估星图该走哪条，给出迁移路径：从当前硬编码状态 → 插件化的分步计划（先抽离、后加载器、后分发）。
- 星图是否应该成为 EXTENSIONS.md 实施顺序里「最小社区界面扩展」的首个真实案例？如果是，实施顺序要不要调整（哪些步骤被倒逼提前）？

### B. 围炉共享数据机制（核心）
- 三个候选方向（可组合，也可提出第四个）：
  1. **Town 服务端新增围炉域数据端点**（KV 或带版本号的文档存储）：服务端是同一家的栈（beings.town），加端点可行但要排期。设计端点形状：读写、版本/冲突策略、权限（成员可读写？owner 门槛？）、新成员加入时如何拿全量。
  2. **消息即状态（event-sourcing over fireside speak/hear）**：星图操作编码为消息事件（建站/移节点/连线/改状态），speak 发事件、hear since 增量回放、revise 维护全量快照消息（32k 上限内的紧凑序列化）。不依赖服务端改动，今天就能做。要设计：事件 schema、快照压缩与重建、新成员冷启动、没装插件的人看到的原始消息长什么样（建议事件消息有可读前缀，如「[星图] N02 状态→测试中」）。
  3. **混合**：先用消息即状态跑通，端点排期后迁移。
- 冲突解决：两人同时改同一节点怎么办（last-writer-wins / 按 seq 单调序 / 简单 CRDT）。星图操作天然偏「整节点替换」，评估 LWW 按 fireside seq 是否够用。
- 实时性：客户端已有 SSE 围炉流，事件消息能否借 SSE 直达插件；延迟预期；离线再上线的 catch-up（since 游标）。

### C. 权限模型
- 谁能改星图：全体围炉成员可写？owner 才能建/删星轨？节点级归属（谁建的节点谁才能移）？给出推荐和理由。
- 成员退出/被移出围炉后，其历史操作保留（消息不可删他人）但新写入被拒——确认这个语义。
- 插件数据访问与围炉成员身份的绑定校验：插件拿什么证明「我在这个围炉里」——复用客户端 Town 连接的成员校验，插件不自己持凭据。

### D. 分发与版本
- Grove 作为星图插件的分发来源（kind=app 只开 GitHub 仓库/Release，不走 Portal Kit 安装——星图作为界面插件走什么 kind？EXTENSIONS.md 说界面信息用 desktop.plugin.json，可与 Kit 同包也可单独发布）。
- 版本兼容：插件版本 vs 客户端 pluginApi 版本；围炉成员插件版本不一致时（A 装了 v1.2、B 装了 v1.0）事件 schema 兼容策略——事件带 schemaVersion，旧版本忽略未知事件还是报错。
- 更新如何到达用户（Grove 升级回退机制 EXTENSIONS.md 已有设计，引用它）。

### E. 最小可行切片（给醇青拍板用）
- 设计文档最后给 2-3 个落地切片选项，例如：
  - 切片1（最快见效）：星图仍留在客户端内，但先实现「消息即状态」的围炉同步层——本围炉成员（都装了开发版客户端）已能共享星图。插件化后置。
  - 切片2（正经路线）：先实现最小插件加载器（Registry+manifest），把星图抽成第一个插件，同步层走消息即状态。
  - 切片3（完整路线）：插件加载器 + Town 围炉数据端点 + 星图插件，一步到位。
  - 每个切片给工作量粗估（S/M/L）、依赖、风险。
